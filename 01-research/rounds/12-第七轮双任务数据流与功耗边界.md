# 第七轮：4K 视频与端侧 AI 的全 SoC 数据流

资料截点：2026-10-20；PUBLIC_ONLY。目标是检验第五、六轮提出的“跨引擎数据流与功耗预算成为 SoC 演进焦点”，不是从公开营销图复原未披露的芯片布线。`[F]` 表示原始资料直接披露的功能/接口，`[I]` 表示将这些功能组成任务链的分析推断，`[U]` 表示目前未核实；厂商效率数字仍标为 `[CLAIM]`。

## 1. 任务 A：持续 4K 视频拍摄

**负载与问题：**摄像头连续产出帧，系统必须在每帧时限内完成曝光/降噪/色调映射、可选的语义处理、预览和编码，同时控制 DRAM 流量及长时间温升。以 3840×2160、60 帧/秒、每像素 10 bit 的*纯单次像素流*作说明，输入下界约为 **0.622 GB/s**（十进制）；真实传感器格式、行间隙、多摄、多次读写、预览和编码缓冲可改变实际流量。这个算式是负载量纲检查，不是任何 SoC 的测量。

```text
[F] 图像传感器
   → [F] ISP/RAW 预处理
   ↔ [F/I] DSP / TPU / NPU 的场景分析或特定视频处理
   → [F/I] 视频编码器、预览/显示缓冲
   → [I] UFS 存储 / 应用分享路径

横向资源：[F] Camera HAL 与图形/视频缓冲接口；[F] 不同产品披露缓存/内存或专用链路
         [U] 各芯片逐段数据是否经 DRAM、SLC 命中率、片上互连拓扑和带宽 QoS
功耗约束：[F] 多引擎和低功耗岛存在；[U] 本任务具体电源域开关、频率与热限功率
```

| 代际例子 | 已被原始资料直接证实的任务环节 | 对阶段问题的架构回答 | 仍不可画实线的部分 |
| --- | --- | --- | --- |
| Snapdragon 820（2015–2016） | 双 Spectra ISP、Hexagon HVX 和低功耗 Sensor Core；4K HEVC 编解码、带宽/帧缓冲压缩；Symphony 管理多个 IP。[V01][V02] | 从 CPU 通用处理转向**固定像素/视频流水线＋可编程视觉＋系统管理** | ISP→HVX 的具体缓冲位置、调用时序和任务级能耗；官方例子不足以拆开工艺收益 |
| Google Tensor / Pixel 6（2021） | Google 称把 Live HDR+ 设计入 Tensor ISP，使其支持 4K60 视频；Tensor TPU 参与视频语音增强，官方结构还披露 System Cache。[V03][V04] | 让影像算法进入实时视频路径，并将视频视觉与音频 ML 配合 | Google 未公开每帧 ISP/TPU/CPU 执行时间、搬运字节数或缓存命中；不能把 TPU 放进所有视频模式的同一条像素流水线 |
| Snapdragon 8 Elite（2024） | 官方称 AI ISP 与 Hexagon NPU 深度集成，Hexagon Direct Link 服务实时语义分割。[V05] | 进一步**缩短 ISP 与 AI 处理协作路径**的厂商设计方向 | Direct Link 的完整物理拓扑、节省了几次 DRAM 往返和端到端视频收益未公开 |
| Dimensity 9500（2025） | Imagiq 1190 的 RAW 域预处理、NPU 辅助追焦、4K120 EIS/4K60 电影视频、NPU/GPU/CPU 动态共享缓存公开可见。[V06] | 高帧率、多算法处理推动 ISP/NPU/缓存与调度并行优化 | 厂商并未证明所有视频模式使用同一共享缓存策略；无法量化视频中 SLC 对 DRAM 的替代率 |

**系统接口而非裸片拓扑：**Android Camera HAL 把 Camera2 等框架 API 接到底层驱动/硬件，capture request/result 使用缓冲接口；这说明视频任务跨软件/硬件边界，不证明某 SoC 的像素流必经特定 cache 或 DRAM。[V07][V08]

**本任务得到的判断：**`[OBSERVATION]` 2015—2025 公开产品连续把视频处理从 ISP/编解码扩到 DSP、TPU/NPU 和更显式的共享数据管理。`[HYPOTHESIS]` “减少跨引擎数据搬运”可能是驱动设计的瓶颈之一，Qualcomm Direct Link 和 MediaTek 共享缓存提供结构信号；目前缺每帧传输/能耗实测，不能称其已被证明为*首要*瓶颈。

## 2. 任务 B：端侧语言或多模态模型推理

**负载与问题：**模型需从存储加载，输入经过预处理，运行时选择执行单元，反复读取权重/状态、更新中间张量，再将输出交给应用。首轮加载、首 token、持续 token、常驻待机是不同测量场景，不能合并成一个 TOPS 数字。

```text
[I] 模型文件/参数（UFS） → [I] DRAM/可用片上存储
     → [F] 编译器/运行时/驱动选择 CPU、GPU、NPU 或分区
     → [F/I] 标量/向量/矩阵执行与中间状态重用
     → [I] token/图像/语音输出 → 应用/显示/音频

可证实的变化：[F] 片内共享存储、SLC/互连、INT2/INT4/FP8、CPU SME2/矩阵、GPU 神经单元
执行不确定性：[F] Android NNAPI 可能分区或回退 CPU；[U] 任一特定手机/模型的实际分区
功耗不确定性：[U] 各电源域占比、DRAM 能耗、热稳态 token/s；厂商规格不提供同口径数据
```

**本任务得到的判断：**`[OBSERVATION]` 端侧 AI 的结构响应已从“新增专用计算单元”转向同时修改**片内存储、外存访问、精度、跨单元调度与软件入口**。`[INFERENCE]` 对 2027—2028 年产品，决定任务效果的可能是首 token/持续输出在固定热预算下的端到端表现；公开资料不足以给出某结构的普遍收益百分比。[V06][V11][V13][V14]

## 3. 两条任务链合看：同一个 SoC 问题吗？

| 相同点 | 视频场景的特殊性 | 端侧 AI 场景的特殊性 |
| --- | --- | --- |
| 多单元协作、缓冲/缓存占用、DRAM 访问和功耗域切换都影响最终体验 | 固定帧期限，输入流不断到来；必须同时处理预览、编码和可能的多摄；过热表现为掉帧或降画质 | 模型加载与反复推理阶段不同；算子/精度/驱动兼容性可能改变实际执行单元；过热表现为延迟或持续 token/s 下降 |

**[INFERENCE]** 因此，“共享缓存更多”不是完整的未来路线。应同时看低功耗任务放置、专用直连/编解码、外存带宽、软件分区和热设计。若只增加缓存，视频的帧期限或 AI 的算子覆盖仍可能限制端到端收益。

## 4. 核心研究目标审计

| 当前目标 | 本轮进展 | 仍缺什么 |
| --- | --- | --- |
| 整体 SoC 如何随历史问题变化 | 已用两条真实任务把 ISP/编解码、DSP/NPU、缓存/DRAM、软件和电源管理串起来；与此前五阶段、八产品对照一致 | 早期通信任务与 2020 年代持续游戏任务还需同样粒度的任务链，以免只围绕 AI |
| 每个阶段的结构变化解决了什么 | 视频帧期限推动固定＋可编程融合；模型推理推动低精度、片内复用和软件可达性；均有原始结构信号 | 每条收益尚无严格因果拆分，尤其具体 DRAM 流量与任务级能耗 |
| 2027—2028 最可能如何演进 | 两条任务都支持“跨引擎数据治理和热预算”作为**候选方向**；2026 已发布更大 NPU 存储与 SI L2/QoS IP | 具体 SoC 是否采用、方案相对更大 DRAM/软件优化的优势仍未知 |
| 本轮是否偏离整体 SoC | **没有。** 任务链同时覆盖计算、媒体、存储、软件、电源与终端热约束 | 下一轮以**通信与持续游戏**两条任务补足全 SoC 场景覆盖，再收敛路线图 |

本轮决策：`UPGRADE` 跨引擎数据路径是重要趋势的**结构证据**；`NARROW` “它已经是首要瓶颈”这一措辞，因缺逐任务流量和能耗测量。下一轮最小公开取证：补通信/持续游戏任务链，同时查可公开的 SoC 数据路径或功耗域技术材料，形成四类任务对比图。若资料不公开，按证据上限封闭该问题，不无限等待测量。

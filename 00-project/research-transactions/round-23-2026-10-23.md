## 本轮要解决的历史研究问题
CPU代际变化如何通过 LLVM 的 ISA features、调度模型和 tune features 传到实际代码？哪些映射只是在编译器源代码中存在，而非手机实测证据？研究目的仍是历史机制与因果解释，不是提出新技术立项。

## 2. 从 LLVM main 可见的结构性线索（不是 release 23.1.4 的验证）
- <https://github.com/llvm/llvm-project/blob/main/llvm/lib/Target/AArch64/AArch64Processors.td> 可看到 TuneA76/TuneA77/TuneA78 分别携带不同 feature 列表。
- TuneA77 包含 FeatureCmpBccFusion；TuneA78 还可见 FeatureFuseCmpCSel、FeatureFuseCmpCSet 和 FeaturePostRAScheduler 等。这仅表明 **LLVM main 的 tuning 启发式存在区别**，并不直接证明手机芯片实现相同融合方式或具备某个定量收益。
- 第22轮将 A76、A77、A78 与 Neoverse scheduling model 的关系记录为某时点 main 的发现；本轮须重新在固定版本上核对 ProcessorModel 定义，不得将调度模型借用视为芯片微架构同一性。

## 3. 接下来逐核核查字段
| 字段 | 必须记录 | 常见误判 |
|---|---|---|
| target 名称 | -mcpu / -mtune 的处理器条目、别名、有效 ISA feature | 名称一致 = 手机 SoC 的实际 SKU 一致 |
| ProcModel | 指向哪一个 scheduling model、定义位置、固定源码 SHA | 借用模型 = 硬件结构相同 |
| tuning features | FeatureCmpBccFusion 等具体列表及定义 | feature 名字 = 可量化硅片事实 |
| 资源与延迟 | SchedMachineModel、SchedWrite、ProcResource、latency、issue width的准确口径 | llvm-mca 静态结果 = 手机IPC/能耗 |
| 历史机型 | IP 公开时间、SoC、手机量产时间分别记录 | IP 发布 = 消费者首发 |
| 证据边界 | OFFICIAL_SOURCE、MODEL_FACT、THIRD_PARTY、INFERENCE、UNKNOWN | 不同证据强度混写 |

### 模型参数核验（不要误读成真实硬件规格）

| LLVM scheduler model | IssueWidth | MicroOpBufferSize | LoadLatency | MispredictPenalty | 源码注释中的关键限定 |
|---|---:|---:|---:|---:|---|
| CortexA57Model | 3 | 128 | 4 | 14 | 以模型/实验性调度参数编码；load latency 为 optimistic |
| NeoverseN1Model | 3 | 128 | 4 | 11 | MicroOpBufferSize 注释写明“Copied from Cortex-A76”；load latency 为 optimistic |
| NeoverseN2Model | 5 | 160 | 4 | 10 | LoadLatency 为 optimistic；buffer 是模型中的 micro-op reorder buffer entries |

**核心审计结论：**
1. 固定 tag 证实了第22轮 main 上观察到的 A76→N1、A77/A78→N2 映射，在 LLVM 23.1.4 中仍然成立。
2. 同时也发现更广泛的模型复用：A72→A57；A710/A715/A720→N2；X2/X3→V2；X4/X925→V3。这个结构性事实说明，不能把 `-mcpu` 名称理解成每个商品核心都拥有完全独立的调度参数表。
3. 这些参数是 LLVM 静态调度模型输入。它们不应直接被当作某款手机芯片真实的解码宽度、ROB 实际容量、load-use 延迟或分支误预测损失；源码注释本身已对若干参数标注乐观估计或从其他核心复制。
4. Tune features 与 ProcessorModel 是不同维度：某些核心即使共用 scheduler model，也可能在融合、寄存器调度或向量化启发式方面具有不同 tuning flags。
5. 本轮只做了源代码核验，没有编译、运行 llvm-mca、benchmark、仿真或设备测量。

### Neoverse V 系列模型扩展核验

| Model | IssueWidth | MicroOpBufferSize | LoadLatency | MispredictPenalty | 源码注释揭示的限制 |
|---|---:|---:|---:|---:|---|
| NeoverseV1Model | 8 | 256 | 4 | 11 | IssueWidth 依据 decode bandwidth 与经验测量设置；load latency 为 optimistic |
| NeoverseV2Model | 6 | 320 | 4 | 10 | 源码说明较低的 IssueWidth 值在经验测量中更好；分支代价注释标注从 N2 复制 |
| NeoverseV3Model | 10 | 320 | 4 | 10 | IssueWidth 注释写明“预计略高于 V2”；buffer 从 V2 复制；分支代价从 N2 复制 |

- `AArch64SchedNeoverseV1.td` blob `0b3afa05789190031b8f34fb0f7706995b7e92c9`: <https://github.com/llvm/llvm-project/blob/llvmorg-23.1.4/llvm/lib/Target/AArch64/AArch64SchedNeoverseV1.td>
- `AArch64SchedNeoverseV2.td` blob `199a4ba0b392fd46b83317cf980a76a444afdf35`: <https://github.com/llvm/llvm-project/blob/llvmorg-23.1.4/llvm/lib/Target/AArch64/AArch64SchedNeoverseV2.td>
- `AArch64SchedNeoverseV3.td` blob `c061d4d9858a8e16493a8db9638fb469bf5da1fe`: <https://github.com/llvm/llvm-project/blob/llvmorg-23.1.4/llvm/lib/Target/AArch64/AArch64SchedNeoverseV3.td>

**新增解释边界：** V2 的 IssueWidth=6 不应因为数字小于 V1 的 8 就被解释为 V2 硬件更窄或更慢；LLVM 文件注释明确表明这是用于代码生成/静态模型的经验选择。V3 的 IssueWidth=10 也带有“预期”性质，且部分 buffer/branch 参数沿用旧模型。由此可见，scheduler model 的参数是建模选择与证据来源混合体，必须逐字段读注释，而不是直接拿参数排列 CPU 代际性能。

### Apple 与 Qualcomm target 覆盖检查（固定 tag）

- **Apple A14/A15/A16/A17/M4/M5：** `AArch64Processors.td` 将这些目标都关联到 `CycloneModel`，但使用不同的 `ProcessorFeatures.Apple*` 和 `TuneApple*`。此外 `apple-m1` 是 `apple-a14` 的 alias，`apple-m2` alias 到 `apple-a15`，`apple-m3` alias 到 `apple-a16`，`apple-a18` alias 到 `apple-m4`，`apple-a19` alias 到 `apple-m5`。这说明 LLVM target 的命名/别名和模型共享需要单独记录；**不能据此推断 Apple A/M 芯片的真实 CPU 微架构相同**。
- **Qualcomm：** 固定文件中存在 `kryo` → `KryoModel`、`saphira` → `FalkorModel` 等目标；本次精确搜索未找到名为 `oryon` 的 processor target。只能写成“LLVM 23.1.4 此文件未发现该命名 target”，不能扩大成“LLVM 完全不支持 Oryon”或推断其指令兼容性/编译器行为。
- **证据边界：** 这些是 LLVM 23.1.4 源码中 target 定义的事实；Apple M 系列的别名主要体现 LLVM tuning target 复用，不能当成手机 SoC 之间的物理核同一性。Qualcomm 的 target 命名覆盖也不等于厂商编译器或手机系统实际使用的 target 配置。

相关固定文件：[AArch64Processors.td @ llvmorg-23.1.4](https://github.com/llvm/llvm-project/blob/llvmorg-23.1.4/llvm/lib/Target/AArch64/AArch64Processors.td)（blob SHA `550c72d2b1ad90bbe1a56c52bcf26bdeb674513e`）。

## 8. 第二批固定版本源码核验：代码生成路径

已核对 LLVM 23.1.4 的以下源码并形成独立矩阵：[代码生成优化入口审计 v0.1](../../03-analysis/LLVM-23.1.4-代码生成优化入口审计-v0.1-2026-10-23.md)。

- `MachineScheduler.cpp`：存在默认启用的寄存器压力调度开关。
- `RegAllocGreedy.cpp`：实现基于 live intervals / live register matrix 的寄存器分配流程。
- `LoopVectorize.cpp`：包含向量化成本模型、VF/IC 选择和代码尺寸相关处理；源码注释也承认某些 epilogue vectorization 仍使用粗略启发式。
- `BasicBlockSections.cpp`：利用 profile-derived block/edge weights 聚类热基本块。
- `clang/lib/CodeGen/CGCall.cpp`：把 SME streaming/ZA 状态相关属性写入 LLVM IR function attributes。

这些源码证明“优化入口存在”，不证明某款手机 SoC 上具体路径已触发，也不证明净性能或能耗收益。仍需区分架构寄存器分配与内部物理寄存器重命名，区分 PGO profile 与真实分支预测器状态。

## 11. 官方性能/能效声明口径审计

已在 [Cortex-A72-A76-A77-A78 跨代因果对照](../../03-analysis/Cortex-A72-A76-A77-A78-跨代因果对照-v0.1-2026-10-23.md) 新增第8节，复核 Arm 原始文章与脚注。

主要修正：A72 的公开历史图中在售设备数据与 A72 实验室预测并存，且 Arm 明确指出收益同时来自微架构和频率；A76 的 35%/40% 声明包含系统/制程比较边界；A77 的单线程、整数、FP、内存带宽和内部结构带宽是不同指标；A78 脚注明确 SPECint2006、单核 1W、2019 设备以及 4+4 集群面积对照，并注明包含架构与制程改进。

**本轮结论：** 官方数字可以作为设计者声明和条件化比较证据，但不能被拼成一条无条件的代际性能曲线，也不能将结构带宽增幅直接映射成应用性能增幅。A78 的比较脚注更明确，但仍属于 Arm 估算且含制程/架构因素，而非独立全机型实测。

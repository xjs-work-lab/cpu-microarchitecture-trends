# 第二十二轮研究事务：移动 CPU 微架构—LLVM 代码生成桥接（2026-10-23）

## 本轮问题
第二十一轮确认的前端/分支、执行资源、寄存器、访存/预取和 SIMD/SME 机制，LLVM 能直接看到哪些、可以改变哪些，以及静态成本模型不能证明哪些？

## 本轮完成
1. 新建[移动 CPU 微架构—LLVM 代码生成桥接矩阵 v0.1](../../03-analysis/移动CPU微架构与LLVM代码生成桥接矩阵-v0.1-2026-10-23.md)，逐项连接 ISA/目标选择、前端/融合、分支/PGO、执行端口/调度、寄存器压力/spill、load-use/MLP、cache/prefetch、SIMD 向量化与 SME/ZA ABI。
2. 新建[第二十二轮 LLVM/调度模型原始来源卡](../../02-evidence/sources/round-22-LLVM代码生成与调度模型原始来源卡.md)，采用 LLVM CodeGenerator、MachineScheduler、Vectorizers、Clang PGO、llvm-mca、AArch64 TableGen 和 SME 文档作为主要直接来源。
3. 新建[第二十二轮桥接证据审计](../../02-evidence/audits/round-22-llvm-hardware-codegen-bridge-audit-2026-10-23.md)，区分机制存在、模型假设与手机端效果证据。
4. 核对 LLVM AArch64 当前可见的 ProcessorModel 映射：Cortex-A76 使用 NeoverseN1Model；Cortex-A77/A78 使用 NeoverseN2Model，同时附加各自的 tuning features。结论仅限于源码建模事实，既不据此断言模型准确，也不据此断言错误。
5. 核对 LLVM Cyclone scheduler model：显式编码 6 µops/cycle issue width、192 µop buffer、4-cycle optimistic load latency、16-cycle mispredict penalty 与执行资源；这证明部分硬件机制会被编译器模型编码，但模型值不等于所有负载下的实机测量。
6. 记录 llvm-mca 的关键边界：静态 IPC/资源压力估计依赖 scheduler model；工具不建模真实 cache hierarchy、load hit/miss 或 store-to-load forwarding，load latency 是模型提供的乐观值。
7. 记录 LLVM register allocator 与硬件 rename PRF 的区别：LLVM 分配 ISA 可见目标寄存器类；内部物理重命名寄存器、ROB/LSQ 动态占用通常不直接作为编译器寄存器分配对象。
8. 将 PGO 的作用限定为使用 workload profile 的分支/函数频率影响块排序和内联，而非直接读取或重构硬件分支预测器。
9. 本轮没有运行 llvm-mca、benchmark、仿真、PoC 或真机测试；没有生成新的手机 IPC/能耗数字。

## 本轮阶段性结论
**[OBSERVATION]** LLVM 利用微架构的路径主要是 ISA/ABI 可见机制、目标后端 latency/resource/tuning 模型、静态依赖/成本分析和真实 workload profile；它不能直接观测大多数隐藏硬件状态。

**[INFERENCE]** 微架构的更宽执行能力、较大乱序窗口或更复杂预取机制，不会自动转化成编译收益。能否获益取决于代码依赖、合法变换、寄存器压力、目标模型质量、数据局部性与 workload 代表性。

## 限制
- 本轮证据来自 LLVM 官方文档和源码体系，能直接证明机制/模型存在，但不是独立手机性能复现。
- AArch64 ProcessorModel 指向 main 分支快照，后续需固定版本/commit。
- 尚未建立常见手机 CPU 型号、设备固件所用 LLVM 版本和真实后端调度模型的完整映射。
- 真实手机的净性能、持续热和能耗效果仍未测量；研究模式为 PUBLIC_ONLY。
